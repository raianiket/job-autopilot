Interview Q&A

Technical
How does the form filling actually work?
Two layers. Structured fields (phone, name, location, dropdowns, radios) are matched by name, id, and placeholder attributes against keyword patterns — for example, input[name*="phone"] or input[type="tel"]. For open-ended text/number questions that can't be pattern-matched (e.g. "Years of React experience"), I extract the label and send it to Claude with the candidate's profile. Experience rule: 5 years if the skill is in the profile, 1 year if not. Specific fields are filled before generic ones so a keyword like "name" doesn't overwrite a field correctly set by "firstname".
Technical
How do you handle multi-step forms?
I run a loop up to maxFormSteps (default 8). Each iteration: fill all fields → check if submit button is visible → if not, count unanswered required fields → if zero, click Next/Review/Continue → repeat. If submit is found, I stop and prompt the user to review and confirm.
Hardest Problem
What was the hardest bug you fixed?
Radio button groups. LinkedIn renders Yes/No questions as radio inputs — each option is a separate input[type="radio"] with required. My original code counted each unchecked radio as one missing required field. A Yes/No question with 2 options counted as 2 unanswered fields — so the tool was auto-skipping jobs that were actually fully fillable. I fixed this by grouping radios by their name attribute and counting the whole group as 1 field, answered if any option in the group is checked.
Technical
How does AI scoring work?
Scoring happens per role, not all at once. After each role's jobs are scraped, that batch (up to 10 jobs) is sent to Claude in one API call. Claude returns a JSON array with index, score 1-10, and a one-line reason. Scores are merged back and written to jobs.csv immediately — so the dashboard shows scored jobs as discovery progresses. If the API call fails, the tool fails open — that role's jobs are kept unscored.
Architecture
Why TypeScript instead of Python?
Playwright has first-class TypeScript support and the typing is extremely useful for browser automation — Page, Locator, and BrowserContext types catch bugs at compile time rather than runtime. Python's Playwright bindings work but you lose the IDE autocomplete and type safety. Also, the whole stack — scraping, CSV handling, HTTP server, Supabase sync — is uniform in one language.
Architecture
Why split into discover and apply phases instead of one command?
Control. After discovery you can open jobs.csv and manually remove any job you don't want to apply to — wrong role, bad company, expired listing. If it were one command, you'd have no chance to review. The two-phase design also means if apply fails midway, you don't need to re-scrape — just re-run apply on the same CSV.
Architecture
How is sensitive data handled? What's gitignored?
config.json (phone, email, model key) and data/ (resume, profile with personal details) are both gitignored. The repo only contains example files with placeholder values. Credentials can also be passed via environment variables — LINKEDIN_PHONE, LINKEDIN_EMAIL, ANTHROPIC_API_KEY, SUPABASE_SERVICE_ROLE_KEY — so nothing sensitive ever touches the filesystem. The session cache file (.linkedin-session.json) is also gitignored — it stores browser cookies with a 30-min TTL and is never committed. The Supabase service role key (write access) is server-side only; the dashboard uses the anon key (read-only, public-safe) injected via Vercel env vars.
Architecture
How does the real-time dashboard work?
Two layers. The local dashboard (npm run dashboard) is a Node.js HTTP server that re-reads results.csv and jobs.csv on every request, with a meta refresh tag that auto-reloads every 15 seconds — so you see jobs populating role by role as discover runs, and results updating as apply runs. The hosted dashboard uses Supabase Realtime — the browser opens a WebSocket channel and subscribes to INSERT events on the job_results table. When apply.ts inserts a new row using the service_role key, Supabase broadcasts it and the dashboard updates without any refresh. RLS allows anon SELECT so the dashboard can read but not write.
Business
Why not just apply manually?
At scale — 50 applications a week — form filling alone takes 3-4 hours. Discovery (finding and filtering jobs) takes another hour. This tool compresses that to under 30 minutes: discover runs unattended, AI filters out weak matches, and apply pre-fills every form so you just review and hit Y. You stay in control of every submission while eliminating all the repetitive grunt work.
Business
Does this violate LinkedIn's terms of service?
LinkedIn's ToS restricts automated scraping and submission. This tool does not auto-submit — it always pauses for human confirmation before sending any application. The browser runs in visible (non-headless) mode. It's a productivity assistant, not a bot — the user manually reviews and approves every single application.
Business
What would you add next?
Three things: (1) Per-job cover letter generation — use the job description + profile to generate a tailored cover letter via AI, replacing the generic one. (2) Job description parsing — open each job URL, extract the description, and use it for better AI scoring and cover letter context. (3) A Slack/email notification when apply finishes a batch — so you can run it overnight and wake up to a summary.
Behavioural
How long did this take to build?
The core — discover, apply, form filling — took about a weekend. The trickier parts like radio button group counting, the multi-step form loop, and handling LinkedIn's dynamic DOM took additional iteration. The AI scoring, Supabase sync, and dashboard were added features built on top of the solid core.
Behavioural
What did you learn building this?
Browser automation at this level taught me that the DOM is far messier than any API. LinkedIn's form markup has no consistent naming convention — you're hunting for signals across name, id, placeholder, aria-label, and parent elements. I learned to write resilient selectors that try multiple strategies and fail gracefully rather than crash. I also learned that config-driven design pays off immediately — every time I wanted to change a value, I was glad it was in config.json and not buried in code.
Behavioural
Why did you choose this project for the Builder Challenge?
Because it's a real tool I actually use. It solves a genuine problem I had, it's fully functional end-to-end, and it demonstrates the skills I use at work — backend Node.js, TypeScript, async systems, API integration, and thinking about security from the start. A portfolio chatbot would have been easier to build but this shows real engineering judgment.

Tradeoffs — 3 decisions (2:30 min)

"CSV as queue over a database — it's human-editable between phases. That's a feature. Keyword matching over AI form filling — one API call per step is slow, expensive, non-deterministic. Keywords are fast, free, deterministic. AI is reserved for scoring, not data entry. Never auto-submit — a bad submission can't be undone. The 5-second confirmation loop is the entire point."

Failure Modes + Close (1:30 min)

"What breaks: LinkedIn's DOM changes — selectors fail silently, jobs save with unknown titles, you update the selector. Rate limiting — slowMo and delays simulate human speed, browser is visible so you see blocks immediately. Radio button miscounting — hit this in production, fixed by grouping by name attribute. The code is at github.com/raianiket/job-autopilot. With more time: per-job cover letters, job description parsing for better scoring, overnight notifications. Thanks for watching."
